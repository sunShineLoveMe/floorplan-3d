## 1. 目标与交付边界

面向个人开发者的首轮真实用户试用：让用户输入自己房间的尺寸和门窗位置，再放入家具、查看 2D/3D、保存并继续编辑。

本次完成一个闭环：**新建矩形房间 → 编辑净尺寸 → 添加和调整门窗 → 摆家具 → 预览 → 保存/恢复**。T02 完成后再做 T03 英制输入；T02 单独完成不等于美国用户试用版全部就绪。

### 必须完成

- 单个矩形房间：名称、净宽、净深、净高；尺寸输入统一为毫米，允许小数。
- 单扇平开门：所属墙、沿墙位置、洞口宽度、高度、铰链端及向内/向外开启。
- 矩形窗：所属墙、沿墙位置、洞口宽度、窗台高度、窗洞高度。
- 门窗新增、选中、数值修改、删除；通过明确的数值操作即可完成，不强制实现拖动门窗。
- SVG 与 Three.js 使用同一份生成几何，门窗洞口真实切开；房间尺寸、面积、视口与漫游起点随房间变化。
- 一次操作一次撤销；取消、输入错误和导入失败不修改当前项目。
- 新旧项目读写、刷新恢复、文件导入导出；保留 v1 与无版本旧文件的既有兼容能力。
- 单元测试、真实浏览器回归、架构和使用说明、带证据的验收记录与明确未测项。

### 本次不做

T03 英尺/英寸解析、多房间拼接、任意多边形/L 形、自由画墙、滑门/飘窗编辑、承重结构编辑、照片/AI 识别、自动家具碰撞与门扇净空提示、家具商品库扩展、登录、数据库、云同步、后台和收费。

继续使用原生 ES Modules、SVG、Three.js、本地存储和 JSON 文件。家具预设与绘制代码可沿用；不引入前端框架、构建器或后端。不推送、不合并、不公开部署。

## 3. 用户操作与交互约定

### 3.1 新建房间

- 提供容易找到的“新建房间”入口；保留“示例户型”入口。
- 表单填写名称、净宽 X、净深 Y、净高。建议初值为 4000、3000、2800 mm；明确是示例初值，需要用户按实测修改。
- 第一版墙厚固定 120 mm，写入数据，界面说明固定值；不把墙厚算入室内净面积。
- 表单是临时草稿：取消、Escape 或关闭都不修改项目，不保存、不增加历史。
- 提交前明确说明将替换当前方案，并提供先导出当前项目的操作；由“创建并替换”按钮一次确认，不重复弹窗。
- 新项目使用新 ID、时间和布局元数据；为空房间，无示例家具、门窗、测量或拆墙状态。保留语言设置，默认 2D、公制显示。
- 替换是一条完整历史记录；撤销恢复旧项目，重做恢复新房间。清理失效选择和未完成手势。

### 3.2 房间编辑

- 房间属性里修改名称、宽、深、高；提交后面积、尺寸线、几何、相机取景和 3D 更新。
- 保持左上室内角为坐标原点；修改尺寸不平移/缩放已有家具，不更换其 ID、尺寸、旋转或颜色。
- 已有测量端点保留绝对坐标，不自动改成随墙测量。提示尺寸修改后需复核家具位置与测量；本次不实现自动越界检测。
- 若缩小房间使任一门窗超出父墙，或降低房高使洞口超高，拒绝整次提交，指出具体门窗；不偷偷删减、缩放或夹紧位置。
- 空值、非有限数、零/负数和超出支持范围的值不能提交。UI 与数据层采用同一组校验规则，并记录支持范围；允许正常的小数毫米，不取整存储。
- 房间名称、材料继续与既有 `rooms` 设置同步；以 `rooms[roomId]` 为名称/材料来源，生成几何从这里读取，避免两个可编辑副本。

### 3.3 门窗编辑

- 在 2D 选择一面墙后添加门/窗；也可在表单中选择墙。提供可选中的图形和列表，选中时高亮所属墙。
- 属性面板明确展示“距起点”的含义；墙两端有方向提示。切换父墙后重新校验当前数值，不暗中移动到合法位置。
- 默认尺寸可预填，但墙不够长时显示错误，用户修改后才能添加。
- 删除门窗、修改一个门窗或一次提交多个字段各产生一条历史。无变化提交不产生历史。
- 新 UI 文案接入现有中英文机制；不扩展为 T08 全站改版。
- 输入框内的删除、撤销等键不能误触画布操作。窄视口下表单、提交按钮和错误信息可访问。

## 4. 数据与兼容设计

### 4.1 采用显式 v2，保留 v1 读取

T02 新增持久化的父墙关系及可编辑房间参数，采用 `format: "floorplan-3d"`、`version: 2`。不能把新的编辑语义偷偷塞进 v1 后声称旧版仍可无损编辑。

v2 保留现有 `geometry`、家具、房间设置、测量、单位与视图等字段，新增 `roomEditor`：

- `roomEditor: null`：原有几何快照，保持既有家具、材料、测量及拆墙操作；不提供矩形尺寸/门窗结构编辑。
- `roomEditor.kind: "rectangle"`：本任务新建的可编辑矩形房间，以房间参数与门窗关系生成几何。

建议数据形状（实现可调整命名，必须补充最终 schema 文档与夹具）：

```json
{
  "kind": "rectangle",
  "roomId": "room-1",
  "width": 4000,
  "depth": 3000,
  "height": 2800,
  "wallThickness": 120,
  "openings": [
    {
      "id": "opening-1",
      "type": "door",
      "wallId": "top",
      "offset": 500,
      "width": 900,
      "height": 2100,
      "hinge": "start",
      "swing": "inward"
    },
    {
      "id": "opening-2",
      "type": "window",
      "wallId": "right",
      "offset": 900,
      "width": 1200,
      "sill": 900,
      "height": 1200
    }
  ]
}
```

- 门窗 ID 全项目唯一且稳定。`top/right/bottom/left` 是房间内的逻辑墙 ID，**不是**生成墙段的 `w0/w1/...`。
- `roomEditor` 参数是矩形结构的唯一编辑来源。纯函数由它及房间设置生成 `geometry`；每次提交参数和几何必须原子更新。
- v2 矩形文件导入时校验参数，并核对生成几何与快照一致；不一致则拒绝，不静默覆盖。统一容差处理浮点比较，不把渲染舍入写回数据。
- v2 几何快照项目直接保留原 `geometry`。不根据“看起来是矩形”自动推断父墙关系。
- 创建自定义房间不能继续盖上 `three-bedroom-a03136c` 模板标记；仅原示例保留该标记。
- 矩形模式不允许拆除生成墙段，`demolished` 必须为空；UI 给出明确状态。原有快照项目的拆墙功能和 `wN` 引用继续保留。

### 4.2 兼容与保存规则

| 输入/动作 | 必须行为 |
| --- | --- |
| v1 完整项目 | 先按 v1 规则校验，迁移为 v2 快照（`roomEditor:null`）；保留几何、墙段顺序、ID、时间、小数、家具高度、拆墙引用、测量与偏好 |
| 无版本旧文件 | 保留已有“确认原模板 → 原文备份成功 → 迁移/替换”流程；结果为 v2 快照 |

| v2 快照项目 | 保持原几何，不尝试转换成矩形编辑器 |
| 错误 JSON、坏字段或未来版本 | 清楚报错，不替换、不改写当前项目 |

新存储键使用 `floorplan-project-v2`。读取顺序为 v2 → v1 → 原无版本旧键，仅当高优先级键**不存在**才回退；存在但损坏时提示恢复，不能静默载入过时项目。

- v1 键 `floorplan-project-v1` 和旧键 `huxing-design-v1` 不覆盖、不删除。读取 v1 后迁移副本，成功保存到 v2 键；失败时保留来源和当前内存项目并显示错误。
- v2 坏数据仍按既有规则在覆盖前写入唯一 recovery 键；备份失败禁止覆盖。
- 不支持迁移后与旧版应用同时编辑的自动合并；不要引入多版本同步系统。

## 5. 几何与渲染约定

### 5.1 坐标和定位

室内净轮廓为 `(0,0) → (width,0) → (width,depth) → (0,depth)`，SVG X 向右、Y 向下。墙厚向室外扩展。

| 墙 ID | 用户名称 | 距离起点 | 沿墙正向 | 内侧方向 |
| --- | --- | --- | --- | --- |
| `top` | 上墙 | 左上角 | 向右，+X | +Y |
| `right` | 右墙 | 右上角 | 向下，+Y | -X |
| `bottom` | 下墙 | 左下角 | 向右，+X | -Y |
| `left` | 左墙 | 左上角 | 向下，+Y | +X |

- `offset` 从上述起点到洞口起边；洞口区间为 `[offset, offset+width]`。
- 铰链 `start/end` 分别为洞口沿墙方向的起端/末端；`inward/outward` 以房间内部为参照。界面用图示辅助，避免模糊的“左开/右开”。
- 窗顶高为 `sill + height`；门高和窗顶高不得超过房高。
- 第一版要求洞口两端离墙角、同墙相邻洞口之间至少保留 1 mm，作为几何有效性限制，不代表结构设计规范。禁止同墙重叠洞口，包括高度不同但投影重叠的窗。
- 数据层检查有限数、范围、唯一 ID、合法父墙、所有枚举及门/窗对应字段；UI 校验不能替代数据校验。

### 5.2 几何生成

- 纯函数生成室内多边形、分段墙矩形、门窗几何、标注、bounds、origin、walkStart、entry 等；不得保留原示例坐标常量。
- 四角墙体连接采用确定的分配规则，避免重复实体、裂缝、负宽或零长墙段。分段排序固定，便于测试与序列化核对。
- 门窗洞口区间从完整墙体中切出。现有 Three.js 建筑模块已经生成门顶墙、窗下墙与窗顶墙；不能另外重复生成同一位置的 `lintels`。
- 门的 `rect/h/c/o/len/height` 与上述铰链/方向规则一致；四面墙、两种铰链、内外开均需验证 SVG 与 3D 相符。
- 净面积严格为 `width*depth/1e6` m²；墙厚和洞口不改变室内净面积。至少显示净宽、净深与面积。
- bounds 覆盖墙体、尺寸标注和外开门图形，2D 自适应与 PNG 不裁掉必要内容。origin 取房间中心，漫游初始位置在室内、目标不与位置重合；无门时允许 `entry:null`。
- 修改房间后 3D 建筑、相机和家具世界坐标使用当前 origin/高度，避免缓存旧值使家具看起来移动。
- 修正已知相关固定值：属性面板墙面面积采用实际 `geometry.height`，继续注明“未扣门窗”；`viewer.js` 门扇漫游阻挡长度当前固定 `.9` m，须使用实际门宽。
- 漫游沿用现有近似碰撞方式；本次修复尺寸一致性，不宣称提供人体通行或门扇净空校验。
